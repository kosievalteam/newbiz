# 사전협의 검토의견서 초안 작성

중앙부처·지방자치단체가 제출한 사전협의 요청서를 검토위원 관점에서 읽고, 회람용 검토의견서 초안을 만든다.
작업은 네 단계로 진행한다: ① 요청서·사업설명서 등 참고자료 검토 → ② 신규사업과 기존사업의 유사도 검사로 상위 10개 후보 제시
→ ③ 상위 3개 후보를 토대로 유사·중복성 검토 → ④ 검토의견서 초안 작성. 아래 「작업 순서」의 1·2 가 ①, 2-1 이 ②·③, 3~6 이 ④에 해당한다.
결과물은 ① 수정용 JSON, ② 미리보기 .md, ③ 발송용 .hwpx(한컴오피스) 세 가지다. `--docx` 를 붙이면 .docx 도 함께 만든다. JSON 하나가 생성·점검·렌더링의 단일 원본이므로
본문은 JSON 으로만 쓰고, 문서 모양은 스크립트에 맡긴다.

## 준비

스크립트는 Python 3.10+ 과 `olefile`, `pydantic`, `click` 이 필요하다(.docx 까지 만들 때만 `python-docx`). 첫 실행에서 import 오류가 나면:

```bash
pip install olefile python-docx pydantic click
```

모든 명령은 스킬 폴더의 `scripts/rd.py` 로 실행한다 (`python scripts/rd.py --help`).

## 작업 순서

### 1. 요청서 읽기

```bash
python scripts/rd.py parse 요청서.hwpx            # 항목별로 정리된 요청서 (신청기관·사업명·추진근거·지원규모·유사중복 점검내용…)
python scripts/rd.py extract 사업설명서.hwpx      # 첨부 설명서·공고문 등은 평문으로
```

- 체크박스(□■) 상태는 추출 과정에서 유실될 수 있다. 선택지 목록이 모두 나열되어 있으면 무시하고 **서술된 내용**만 근거로 삼는다.
- `parse` 가 항목을 찾지 못하면 `extract` 로 원문을 보고 직접 읽는다. 양식이 조금 달라도 별지1 라벨(신청기관·사업명·사업개요·추진근거·지원규모…)은 같다.
- 요청서와 설명서가 서로 다른 수치(예산 합계, 성과지표)를 적고 있으면 그 자체가 검토 포인트다. 메모해 두었다가 사업성과·지원규모 dash 와 reviewer_notes 에 반영한다.

### 2. 작성 규칙과 예시 읽기

- `references/writing_rules.md` — 위계(○→-→*), 평가축별 표준 구성, 판단어휘, 표기 규칙. **반드시 먼저 읽는다.**
- `references/exemplars/` — 실제 회람된 검토의견서 6건(익명화). 신설/변경, 동의/권고, 지자체/부처 중 지금 사안과 비슷한 2건을 골라 읽고 문체와 밀도를 맞춘다.
  - 2026-178 세부사업 신설·적합성 동의·유사중복 권고 (소상공인 인력)
  - 2026-184 세부사업 신설·전 항목 권고·내역사업 2개 (부산 R&D)
  - 2026-171 사업내용 변경·적합성 권고 (창업센터)
  - 2026-175 변경·전 항목 권고·유사중복 상세 비교 (오픈이노베이션)
  - 2026-180 내역·내내역 신설·유사중복 권고 (창업허브)
  - 2026-181 내내역 신설·내역별 유사중복 비교 (판로개척)

### 2-1. 유사도 검사: 기존사업 상위 10개 후보 → 상위 3개로 유사·중복성 검토

기존사업 비교 대상은 기억이 아니라 유사도 분석 결과에서 고른다. 결과 파일이 있으면 그것을, 없으면 만들 수 있는지 확인하고, 둘 다 안 되면 마지막 수단으로 모델 지식을 쓴다.

```bash
# (a) 분석 산출물(similarity_scores.xlsx 또는 top10.json)을 사용자가 주었거나 저장소 similarity/results/ 에 있으면
python scripts/rd.py similar-top 유사도_산출결과.xlsx            # 상위 10개 표 (사용자에게 그대로 제시)
python scripts/rd.py similar-top 유사도_산출결과.xlsx --json      # 검토의견 JSON 의 similarity 필드에 넣을 값
python scripts/rd.py similar-top 유사도_산출결과.xlsx --unit 내역1_금융AI실증매칭   # 내역사업별 순위

# (b) 산출물이 없고 저장소(kosievalteam/newbiz)의 similarity/similarity_check.py 와 기존사업 자료(공고정보 xlsx, Supabase public.biz 추출 JSON)에
#     접근할 수 있으면 README 의 사용법대로 실행한다 (torch·sentence-transformers 필요, bge-m3 모델 다운로드).
#     새 협의사업은 similarity/new_project_profile.json 의 4개 축(사업목적·지원대상·지원내용·전달체계) 서술을 요청서 내용으로 바꿔 쓴다.
```

- **후보 제시(②)**: 상위 10개를 순위·사업명·부처·기관·종합 유사도·축별 유사도 표로 사용자에게 보여 주고, 3개 묶음(동일 수행기관 사업 / 같은 기능 사업 / 범용 사업 등)으로 짧게 해석한다. 유사도는 선별 지표이지 중복 판정이 아니라는 점을 한 줄 적는다.
- **상위 3개 심층 검토(③)**: 상위 3개를 유사·중복성 축의 비교 대상과 사업간 비교표의 기존사업 열로 쓴다. 각 후보의 사업목적·지원대상·지원내용·지원방식을 요청서와 대조해 「차별성 인정 / 유사성 확인 / 중첩 소지」를 정하고, 예산·지원규모·대상은 예산서·공고문(또는 Supabase `public.biz`)에서 확인한 값을 쓴다. 확인하지 못한 값은 `[확인 필요]`.
- 4~10위 중 검토에 의미 있는 사업(예: 교육생이 겹치는 인재양성 사업)은 dash 의 각주나 개선의견에서 언급하고, 비교표에는 넣지 않는다.
- 결과 표는 검토의견 JSON 의 `similarity` 에 넣어 문서 끝 〈참고〉 유사도 분석 결과로 출력되게 한다(`render --similarity 파일` 로 붙일 수도 있다).
- 산출물도 분석 환경도 없을 때만 모델 지식으로 기존사업을 고르고, 그 사실을 reviewer_notes 첫 줄에 적는다.

### 3. 판단 세우기

JSON 을 쓰기 전에 평가축별 결론을 먼저 정한다. 아래는 검토자들이 실제로 권고로 돌리는 전형적 사유다.

| 평가축 | 동의 | 권고로 돌리는 전형 사유 |
|---|---|---|
| 사업 타당성 | 법령·상위정책·정책수요 확인, 성과지표가 목적과 연계 | 성과지표 미설정, 산출지표(운영 개소수 등)만 설정, 세부사업 단위 지표, 요청서–설명서 지표 불일치 |
| 사업 적합성 | 지원내용이 목적에 부합, 산출근거(단가×수량) 제시, 수행체계 적절 | 지원물량·단가 미제시, 성과가 기업에 귀속되는데 자부담 미설정, 사업명–지원내용 불일치, 선정기준 미제시, 운영주체 미확정 |
| 유사·중복성 | 기존사업과 목적·대상·내용 중 차별성 확인 | 중앙부처 기존사업과 대상·내용 유사, 유사중복 자체점검표 미작성·일부 분야만 점검 |

- 종합의견은 세 축 중 하나라도 권고이면 권고.
- 권고로 판단한 사항은 빠짐없이 「개선의견」에 ○ 항목으로 나타나야 한다. 반대로 개선의견에만 있고 본문 dash 에 근거가 없는 권고는 만들지 않는다.
- 비교 대상 기존사업은 2-1 의 유사도 상위 3개다. 상위 3개가 모두 같은 수행기관이면 「통합·연계」가 핵심 쟁점이 되고, 부처가 다르면 「중복수혜 방지 기준」이 쟁점이 된다. 기존사업의 예산·지원규모를 확신할 수 없으면 `[확인 필요]` 를 붙이고 reviewer_notes 에도 적는다. 지어내지 않는다.

### 4. JSON 작성

`assets/opinion_template.json` 을 복사해 채운다. 필드 설명은 `references/schema_guide.md`. 핵심만 요약하면:

- `overview.사업명` 은 `협의번호. 사업명 / 요청사유` (협의번호를 모르면 `사업명 / 요청사유`). `신청기관` 에는 담당자 성명·연락처를 쓰지 않는다.
- `validity / suitability / duplication` 의 `headline` 은 `(사업 타당성) 법적근거 및 정책수요 측면 타당하나, 성과지표 보완 필요, “권고안 제시”` 처럼 평가 영역 + 결론을 한 줄에 담는다. 헤드라인에 쓴 영역 단어와 dash 의 `label` 이 1:1 로 맞아야 한다 (check 가 검사한다).
- dash 는 「(라벨) 사실 압축 + 판단어휘」. 박스의 사실을 되풀이하지 않고 검토자의 판단(…인정 / …적절 / …부합 / …필요)으로 끝맺는다. 마침표 없음, 70자 내외.
- 각주는 `notes` 에 넣고 본문에 `*`, `**` 로 표시한다. 법령은 「법령명」 조문(조문명), 기존사업은 `(사업명, 부처) 지원대상·내용`.
- `content_box` 는 사실만, `check_box.lines` 는 영역별 `(원안 동의)` / `(권고안 제시) 보완 요지`.
- `improvements` 는 `(성과관리)` `(사업 운영방식 보완)` `(중복수혜 방지)` 같은 라벨 + dash. 모두 동의면 headline `해당 없음` 1건.
- `comparison.rows` 는 사업부서·사업구조·사업기간·지원예산·사업목적·수행기관·지원내용·지원규모·지원대상 순, 각 행은 `[구분, 값…]` 로 열 수와 일치.
- `similarity` 에는 2-1 의 상위 10개(`similar-top --json` 출력)를 넣는다. 없으면 빈 값.
- `reviewer_notes` 에는 검토자가 발송 전 확인할 것(협의번호·검토자 미기재, 확인 필요 수치, 체크박스 유실로 추정한 항목, 요청서 내부 모순)을 적는다. 본문에는 출력되지 않는다.

### 5. 자가 점검

```bash
python scripts/rd.py check 초안.json
```

오류(헤드라인–요약표 불일치, 헤드라인 영역에 dash 없음, 권고인데 개선의견 없음, 점검 박스 불일치, 비교표 칸 수)는 0건이 될 때까지 JSON 을 고친다.
주의(장황한 dash, 각주 표시 누락, 회피 표현, 연도 따옴표)는 하나씩 읽고 타당하면 고친다. 점검을 통과해도 사용자 지침대로
표현과 개조식 논리의 정합성을 한 번 더 눈으로 검토한다 — 특히 같은 사실을 dash 와 박스에 중복 서술하지 않았는지, 권고 사유가 본문과 개선의견에서 같은 말로 쓰였는지.

### 6. 출력과 전달

```bash
python scripts/rd.py render 초안.json -o output --name 검토의견서_초안_기관_사업명 --appendix 요청서.hwpx
```

`.hwpx`(참고1 요청서 원문 첨부, 마지막 장에 검토자 확인 메모) 와 `.md` 가 만들어진다. Word 파일이 필요하면 `--docx` 를 붙인다. 사용자에게 hwpx·md·json 을 함께 주고,
답변에는 ① 평가축별 결론과 핵심 권고 사유, ② reviewer_notes 의 확인 필요 사항, ③ 정합성 점검에서 고친 점을 짧게 적는다.
수정 요청이 오면 JSON 만 고치고 `render` 를 다시 돌린다.

## 기존 검토의견서를 점검·윤문해 달라는 경우

`python scripts/rd.py extract 검토의견서.hwp` 로 본문을 꺼내 같은 JSON 구조로 옮긴 뒤 `check` 와 writing_rules 의 금칙 표현·표기 규칙으로 점검하고, 수정본을 `render` 로 낸다. 기존 문서의 판단(동의/권고)은 근거 없이 바꾸지 않고, 바꿔야 한다면 reviewer_notes 에 사유를 남긴다.

## 지면 구성 (참고)

```
1. 협의신청사업 및 검토의견 개요
   □ 협의신청사업 개요 (사업명·신청기관·지원유형·특이사항·검토자)
   □ 사업개요 추가정보 (근거법령·상위정책·사업목적·지원대상·지원내용·지원규모·전달체계·연계사업)
   □ 검토의견 요약 (종합/타당성/적합성/유사중복 : 동의|권고)
   ※ 유사중복검토 사업 (부처·사업명·검토의견)
2. 검토의견
   1. 종합의견  ○ (사업 타당성) / ○ (사업 적합성) + [사업내용] ⇩ [사업내용 점검] / ○ (유사‧중복성)
   2. 개선의견  ○ (라벨) 헤드라인 + dash
〈사업간 비교표〉
참고1. 협의요청서 (선택)
```
